# 需求简报器

一句话想法 → 一份 8 行以内的迷你简报 → 用户确认 → 动手。
**目的不是流程，是保真**：让 AI 拿到的是"意图"而不是"猜测的空间"。

## 为什么需要（真实教训）

深脑项目里，"人物系统"从一句『有没有可能设计一种比较好的交互方式』长出了
待选库/批量处理/合并建议一整套重机器——两天后用户自己要求减掉一半。
**没有验收标准的开放需求，AI 默认会过度建设。** 简报就是刹车。

## 简报模板（AI 产出，等确认）

```
【需求简报】<一句话名字>
意图     ：用户想要什么（一句话，用户视角）
为什么   ：现在的痛 / 为什么值得做（一句话）
验收     ：做完的判据，1-3 条可检验的（"一屏能看到 20 个人的关键信息"这种）
不做什么 ：本次明确不碰的（防蔓延）
影响面   ：动哪些页面/表/管线；要不要迁移
默认值   ：AI 拿不准但先按 X 做的点（标出来，错了好改）
```

## 执行规则

1. **最多问 2 个澄清问题**，其余全部给默认值并在简报里标注——绝不用问题轰炸换安全感。
2. **小事跳过简报**：改文案、藏入口、一行修复、调样式——直接做，做完一句话说明。简报只给"会长出结构"的需求用。
3. 简报被确认后：动手 → typecheck/测试绿 → 一次性问部署授权。中途不再反复确认。
4. 用户若在简报阶段就说"直接做"，尊重，但仍把「验收」和「不做什么」写在动手前的第一条回复里。

## 金标准案例（用户写得最好的三条请求，照这个学）

1. **用户故事式**：「我作为一个用户，会有各种各样的录音……我愿意把所有的录音材料都放到这个平台当中去。未来这个平台的功能应该是：1. 项目管理…」——愿景+角色+编号功能，AI 可以直接架构。
2. **系统捋一下式**：「错得太大了。我们捋一下，现在这个产品当中到底怎么来做这个功能？」——不要补丁、要重新设计的信号，明确邀请系统性方案。
3. **结构化概念式**：「1. 确定性人物库：… 2. 待选人物库：… 3. 常见人物识别：…」——编号+概念命名+每条一句话定义，等于口述 spec，一次到位。

## 反模式（避免）

- 「经常失败」「很多地方不对」→ 给不出根因。改成：次数/最近一次的链接/截图。
- 「都需要做下」→ 连安全分类器都不认它是授权。改成明确动词+对象：「三个都做，部署到 122+43」。
- 一条消息混 bug+新功能+哲学 → 至少编号分开，标 P0/P1。
