# IoT 设备接入

一句话原则：**对方的文档是线索，不是事实；对方的推送是信号，不是数据源；
而你自己的丢弃路径，必须比对方的失败更显眼。**

接入失败通常不是「连不上」，而是「连上了、也在推、但东西没进来，而且看不出来」。

---

## 第 0 步：接入前必须问清的七件事

不问清就开工，后面每一件都会变成两天的排查。

1. **有几套环境？** 测试和生产的 HOST、凭据是否不同？设备在哪一套？
   （实战：我们的 HOST 指着测试环境，管理平台是生产环境，症状是「查询接口永远返回 0 条」。）
2. **凭据的权限范围是什么？** appId 能看到哪些设备？账号级还是设备级授权？
   谁能改这个范围、改了会不会通知我们？
   （实战：对方把设备移出授权范围，接口从「有数据」变成 `10013 无权限`，我们以为是「对方删了数据」。）
3. **回调有哪几类、各自的触发条件？** 尤其：**同一件事会不会推多次？多次之间字段怎么变？**
4. **回调里有没有唯一 ID？它在一次业务生命周期里会不会被复用？**（见第 3 步，最贵的坑）
5. **文件直链有没有有效期？** 过期后还能不能重新取？记录本身会不会被清理？
6. **推送失败会不会重试？能不能手动重推？** 能重推就有救命通道，第一时间确认。
7. **回调地址的鉴权怎么配？** token 放 header 哪个字段 / query / body？
   （对方常常只给你填一个字符串，不告诉你它会放在哪。）

---

## 第 1 步：先建探针，别信文档

**不要根据文档写代码然后调试。先写一个最小探针，把每个接口的真实返回打出来。**

```js
// 要点：打真实响应体，不是自己解析后的投影
const r = await fetch(HOST + path, { method: 'POST', headers, body: JSON.stringify(payload) })
console.log(await r.text())      // ← 不是 await r.json()
```

必须实测确认的字段（文档最常错的地方）：

| 要问的问题 | 为什么 |
| --- | --- |
| 分页信封是 `data.rows` 还是 `data.records`/`data.list`？ | 猜错的表现是「total=0」，看起来像没数据 |
| 时间参数叫 `stopTime` 还是 `endTime`？时区？格式？ | 参数名错了对方通常不报错，直接返回空 |
| 声称唯一的业务号（orderNo 之类）真的有值吗？ | 实战：恒为空串，归并键只能从 fileName 解析 |
| 「结束标记」和「文件可下载」是同一件事吗？ | 实战：`endMark:1` 可与 `fileUrl:""` 同时成立 |
| 复杂参数要不要嵌套？ | 实战：起止时间必须包在 `timeSlots` 数组里，否则「非法参数」 |
| 文件名有哪些变体后缀？ | 实战：`_stereo`/`_left`/`_right`/`_cut_xxx`/`_voice_print`；用宽松正则会静默跳过整条 |

**判据：线上失败而单元测试是绿的，第一件事是去看测试断言的是什么形状，不是改实现。**
测试会忠实地固化你的误解。实战里我照着自己的误解改了四轮参数，
才想起来去打印真实请求体——那本该是第一步。

## 第 2 步：摄取模型——三条路互为兜底

单靠任何一条都会在某天断掉。按可靠性从高到低：

```
① 回调即捕获    对方推完成通知 → 立刻落台账 → 立刻取文件
② 台账直连      从①存下的回调里取直链下载，不碰对方任何查询接口
③ 对账拉取      定时查对方清单（回看 N 小时），补 ①② 漏掉的
```

**关键设计：② 必须存在。** 它是唯一不依赖「对方的查询接口 + 我们的查询权限」的路径。
实战里对方把设备移出授权范围，①③ 同时死掉，只有 ② 还活着——因为完成回调里
直链和时长都是现成的，根本不需要再问对方一次。

把降级写成显式的三级 fallback，**每一级失败都记日志说明为什么降级**，不要静默 `return null`。

### 落台账优先于处理

回调进来先无条件写一行台账（原文 + 处理状态），再谈业务。
台账是后面所有排查的唯一依据，也是 ② 的数据来源。

---

## 第 3 步：幂等键——最容易错、后果最重

**绝不直接把对方给的 eventId 当幂等键。**

实战里对方在**同一次录音的生命周期内复用同一个 UUID**：

```
开始录音   eventId=3f6289c8…  fileUrl=""        ← 存下了
录完上传   eventId=3f6289c8…  fileUrl="http…"   ← 键重复，被当成重推丢弃
```

**丢掉的恰好是唯一带数据的那条。** 而日志只说「重放了」，看起来一切正常。

正确做法：**键 = 对方的 ID + 这条消息的「状态」**。

```ts
// 状态只取「有没有」，不取值本身
const ready = Boolean(fileUrl || leftFileUrl || rightFileUrl)
return `${eventId}#${ready ? 'ready' : 'pending'}#${fileName}`
```

三条判据：

- **只取「有无」，不取 URL 本身**——签名直链每次重签都不同，取了就等于没有去重；
- **带上文件名**——分片是不同的文件，不能互相顶掉；
- **状态维度要覆盖对方所有会变的字段**，先用探针把一次完整生命周期的推送全录下来再定键。

---

## 第 4 步：丢弃路径必须留痕（红线）

接入类问题的头号形态：**「对方没发」和「我们没接住」长得一模一样。**
两边都是「什么都没发生」。实战里这个形状出现了四次，每次第一判断都怪对方，每次都错。

所以：

- **每一条丢弃都要有日志，且带上判据本身**（丢弃时的键、判成了什么、依据是什么）。
  只写「重放了」等于没写——它和「对方没推」在日志里长得一样。
- **界面上要有收发台账**：收到了什么类型、什么时候、我们拿它做了什么。
  让用户自己能判断卡在哪一环。
- 台账要写清**边界**：被去重丢掉的那些**不在台账里**（它们没落行）。
  界面上必须明说，否则用户会把「台账里没有」读成「对方没推」——同一个坑再来一次。

对方平台一般有自己的「推送日志」，那是**对方发了什么**的真源；
你的台账是**你收到并做了什么**的真源。两边对照才能定位。

---

## 第 5 步：时间敏感的摄取要有独立节拍

**分类依据不是「重不重要」，是「晚了会不会永久丢」。**

带签名的直链会过期、对方的记录可能被清理——晚一小时可能永久取不到。
而「补跑历史数据」晚一天没关系。这两类不能排在同一条队里。

实战栽了两次，第一次的修法是错的：

1. 摄取排在共享主循环的「维护支路」里，几小时没跑。**上移到前面，以为好了。**
2. 没好。主循环里的支路是**顺序执行**的，其中有 LLM 任务，一次迭代三十多分钟。
   摄取每次迭代只轮到一次，60 秒的 ticker 实际节拍是三十多分钟。

> **调顺序只改「谁先谁后」，改不了「一次迭代有多长」——最慢的那个决定所有人的节拍。**

正确做法：**给它自己的 `setInterval`**，带重入保护（上一轮没跑完就跳过这一拍）+ `unref()`。
前提是它与主循环没有共享状态（不占并发槽、不抢配额）——摄取通常满足。

**判据：修调度问题先量真实节拍，再改结构。**
「谁在谁前面」是静态属性，「多久跑一次」是动态属性，前者推不出后者。
看一眼日志里两次执行的时间差，比读十遍代码有用。

---

## 第 6 步：约束里区分「不变量」与「实现细节」

数据库约束会把**写它时的世界观**固化下来。接入方式一变就成了阻碍。

实战：`succeeded ⇒ provider_task_id 非空`。写的时候是对的——那时「成功」只有一条来路
（提交合并任务 → 轮询 → 入库）。后来有了直连入库，全程没有对方的任务号，
表现是**数据已经进库、状态却标不上，于是无限重试、反复重下同一份大文件**。

放宽时必须分清：

- **不变量**：东西到底拿到了没有（`succeeded ⇒ 有会话/有文件`）→ **一个字都别动**
- **实现细节**：走的哪条路、有没有对方的任务号 → 可以解绑

**放宽约束时最容易顺手把真正的不变量一起删掉。**
所以每次改约束都配一条契约检查，专门断言那个不变量还在。

## 排障速查表

| 症状 | 先查什么 |
| --- | --- |
| 查询接口返回 0 条 | ①参数名/信封字段猜错 ②环境不对（测试 vs 生产）③**权限范围**（对方是否报「无权限」） |
| 回调「没来」 | 先查**自己的丢弃日志**，再去对方推送日志对照。别先下结论 |
| 回调来了但没进库 | 幂等键是不是把它当重放了（第 3 步） |
| 台账有、文件没下来 | 直链是否过期；降级链有没有静默 `return null` |
| 摄取时有时无、间隔忽长忽短 | 量两次执行的时间差；多半被别的慢任务拖着（第 5 步） |
| 状态标不上、无限重试 | 数据库约束是不是要求了这条路径没有的字段（第 6 步） |
| 明明启用了却一次没跑 | 打一行**无条件**探针日志，确认分支到底有没有被执行到 |

## 验收清单

- [ ] 三条摄取路径各自单独验证过，且**任意断掉一条，其余仍能把数据拿进来**
- [ ] 幂等键用一次完整生命周期的真实推送验证过（含对方重复推送）
- [ ] 丢弃路径有日志且带判据；界面上有收发台账，并写明它看不到什么
- [ ] 摄取有独立节拍，且**量过真实间隔**（不是读代码推断）
- [ ] 凭据只在服务端环境变量里（`chmod 600`），不进仓库、日志、文档
- [ ] 文档与实测的差异整理成一张表，**发给对方**——别的接入方大概率也在踩

| 合并任务参数平铺 | 起止时间必须嵌在 `timeSlots: [{startTime, endTime}]`，否则 `1002 非法参数` |
| 每条回调一个 eventId | **同一次录音的开始与完成共用同一个 eventId** |
| — | 文件名后缀有 `_stereo` / `_left` / `_right` / `_cut_xxx` / `_voice_print` |
| — | 完成回调里的文件就是**整段合并好的**，多数场景根本不需要合并任务 |
| — | 时间一律 UTC+8、`yyyy-MM-dd HH:mm:ss`；管理平台按浏览器时区渲染（易差 1 小时） |
| — | v2 与 v3 接口路径相同，可直接换 HOST |
