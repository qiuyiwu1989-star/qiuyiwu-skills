## 治理神经① 定位

**为什么是「治理神经」而非独立框架**：意图管理贯穿多个框架的内部，不能被单一框架完整承载——F14解决「结果意图如何定义」，F15解决「上下文意图如何设计」，F07/F10解决「组织层面谁负责意图翻译」。治理神经①是把这些分散实现统一起来的认知锚点。

## 意图管理的三个层次

### 层次一：战略意图层（组织→编排者）
**问题**：企业的战略意图如何被翻译成Agent系统的任务规格？

**核心挑战**：战略意图天然是模糊的（「提升客户满意度」「降低运营成本」），而Agent需要精确的任务规格才能有效执行。这个「模糊→精确」的翻译过程，是编排层（Agent Owner）最核心的工作。

**操作要点**：
```
战略意图翻译三步法：
1. 意图澄清：这个意图背后，什么叫「成功」？（对应JTBO的结果定义）
2. 边界定义：Agent在哪些范围内可以自主决策？哪些必须升级？
3. 验证标准：如何知道意图被正确理解和执行了？
```

### 层次二：任务意图层（人类→Agent，单次交互）
**问题**：用户在单次交互中如何准确表达需要Agent完成的任务？

**核心挑战**：人类表达习惯依赖共同背景知识和隐性理解，而Agent缺乏这些——它只能基于显式表达做判断。「帮我改一下这篇文章」对人类听众意味着一套复杂的期望，对Agent来说是高度欠定义的指令。

**意图表达质量的四个维度**：
```
① 结果明确性：什么叫做完了？（不是「做得好一点」，而是「达到X标准」）
② 范围清晰度：在哪个范围内执行？不碰哪些东西？
③ 约束条件：有什么不能做或必须遵守的限制？
④ 验证方式：我怎么知道你做对了？
```

**意图表达模板**（高质量任务规格）：
```
任务：[具体动作描述]
结果标准：[完成后的状态描述，参照JTBO结果定义]
范围边界：[可以做什么，不要动什么]
约束条件：[必须满足的限制]
输出格式：[期望的交付物形式]
验证方式：[我如何确认任务完成]
```

### 层次三：上下文意图层（系统设计→模型，持续运行）
**问题**：产品设计层面如何确保模型在每个决策点都能「理解」当前任务的真实意图？

**核心挑战**：在持续运行的Agent系统中，意图不是只在「下达命令」时传递，而是通过上下文工程在每个推理时刻注入。上下文六层（F15）本质上是「持续性意图传递机制」的工程实现。

**关键设计要求**：
```
系统提示（L6）= 角色意图 + 能力边界 + 行为规范
任务上下文（L3）= 当前任务意图 + 背景约束 + 验证标准
用户输入设计（L2）= 引导用户表达更高质量的任务意图
```

## 意图损耗：四个常见的意图传递失真点

```
失真点① 战略→任务：管理者用业务语言表达意图，编排者用技术语言翻译
  → 危险：翻译过程中目标被替换（满足了指标但没有实现真实目标）
  → 防止：JTBO结果定义作为翻译的验证标准

失真点② 任务→提示词：产品经理用自然语言描述需求，工程师用提示词实现
  → 危险：实现了字面含义，但没有实现背后的用户意图
  → 防止：Context-First Design作为转译框架

失真点③ 提示词→上下文：提示词写好了，但运行时上下文信息不足
  → 危险：模型在信息不完整的条件下做出「合理但错误」的判断
  → 防止：上下文六层完整性检查（F15的S2）

失真点④ 上下文→输出：信息完整，但模型输出不符合用户真实期望
  → 危险：意图已经被准确传递，但模型理解与用户理解存在gap
  → 防止：Re-delegation Rate（F16）+ Override Rate（F16）追踪用户是否真正满意
```

## 意图管理与其他框架的联动

```
F14（JTBO）：定义「结果意图」——什么叫成功，而不只是任务完成
  → 意图管理的第一步是准确定义意图的内容

F15（Context-First Design）：实现「上下文意图工程」
  → 意图管理的工程实现：确保每个决策点的上下文包含任务意图

F07（Agentic Network）：「意图在节点间如何传递」
  → 意图在人类节点→编排节点→Agent节点之间的传递协议

F10（岗位体系/意图翻译者角色）：「谁负责意图翻译」
  → 意图翻译者是HACell中最核心的人类价值：把组织意图翻译成Agent可执行的规格
  → 「说得准」比「做得快」更稀缺，是人类在人机协作中不可替代的核心价值之一
```

## 意图质量的自检清单

激活本治理神经时，对当前的意图表达/设计进行检查：

```
战略意图层检查：
  □ 「什么叫成功」是否被具体定义（不接受「更好」「提升」等模糊描述）
  □ 是否完成了JTBO结果定义（结果+验证+时间+所有权）
  □ 意图传递链条：战略意图→任务规格→系统提示，每个环节是否有显式记录

任务意图层检查：
  □ 任务规格是否包含四个维度（结果/范围/约束/验证）
  □ 是否存在「意图表达者认为显而易见但Agent无法推断」的隐性假设
  □ 给Agent下的指令，能否通过「如果一个不了解背景的新人看到这个指令，能做对吗」的测试

上下文意图层检查：
  □ 系统提示中的角色意图是否精准（没有「尽力而为」之类的模糊描述）
  □ 任务上下文（L3）是否在每次任务时完整注入
  □ 用户输入设计（L2）是否引导用户提供更高质量的意图表达
```

## SKILL激活示例

**触发场景1**：「我的Agent总是做不对，怎么改进提示词？」
→ 先用意图管理三层框架诊断：是战略意图没有清晰定义（S1），还是任务意图在下达时不完整（S2），还是上下文工程没有把意图准确传递给模型（S3）？通常「改提示词」解决的是S3，但根因可能在S1或S2。

**触发场景2**：「产品经理和工程师对这个Agent要做什么争执不清」
→ 这是意图翻译失真点②的典型表现。建议用JTBO结果定义框架，先对齐「什么叫成功」，再讨论「如何实现」。

**触发场景3**：「用户说Agent没有理解他的意思」
→ 对照意图表达质量的四个维度，分析用户的指令是否存在结果不明确/范围不清晰/约束未说明的问题，并优化交互设计引导用户提供更完整的意图表达。
