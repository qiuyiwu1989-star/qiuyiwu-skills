# Vibecoding PM

## Purpose

Vibe coding 的失败根因不是 AI 写不好代码，而是意图蒸发：对话是需求文档，但对话会过期。本技能把项目管理还原为上下文工程——将意图（specs）、状态（tasks）、决策（decisions）、验收标准（tests）全部外化为文件，使任何一个新会话的 AI 都能无损接班。

核心原则：人做决策，AI 做执行，测试做验证。

第二原则：**委托的深度受限于验收带宽。** 人只能以阅读速度验收，所以本能地把任务切碎、切浅，好让自己看得过来——这正是大多数人用 AI 只敢让它写小片段的原因。要放开委托深度，唯一的办法是把验收前移并机器化：不是人变快，是让验收由机器执行。

## Gear System（档位机制）

先判断项目档位，再决定管理重量。过度流程是创造力的敌人，流程缺失是可维护性的敌人。

| 档位 | 适用 | 必备文件 | 验证方式 |
|---|---|---|---|
| G1 原型档 | 验证想法、周末项目、demo | `CLAUDE.md` | 能跑就行 |
| G2 产品档 | 会被真实使用、多次迭代 | + `specs/` + `TASKS.md` + `DECISIONS.md` | 每个 spec 有验收清单 |
| G3 生产档 | 上线、多人、有 SLA | + 自动化测试 + CI | 测试闭环，spec 与测试互相追溯 |

判定规则：
- 项目预期寿命超过两周，或代码超过 10 个文件 → 至少 G2。
- 有真实用户数据、支付、安全边界 → G3。
- 用户明确说"随便试试" → G1，不要强加流程。
- 档位可升不可降：原型验证成功后，第一件事是升档，而不是继续堆功能。

## Operating Rules

- 每次会话开工先读 `CLAUDE.md` 和 `TASKS.md`（若存在），收工前必须更新它们。没有例外。
- G2 及以上：先有 spec 再写代码。任何超过一次对话能完成的功能，先写 spec。
- Spec 上限 200 行。写不下说明功能该拆分，不是说明 spec 该加长。
- 每个 spec 必须包含「不做什么」（Non-Goals）。约束比目标更能控制 AI 的发散。
- 方案中凡是能用确定性规则算出来的部分，不交给模型生成。模型生成的确定性字段会产生静默错误，且无法定位。
- 质量控制放在验收端，不放在生成端。用更多次生成去"投票投出正确答案"，比用确定性规则拦截贵得多，也不可靠。
- 每完成一个任务做一次 git commit，commit message 引用任务或 spec 编号。
- 不要伪造完成状态。测试没跑通就在 TASKS.md 标记 `blocked`，写明卡点。
- 决策一旦做出（选型、架构、取舍），当场写入 `DECISIONS.md`，包含日期、选项、理由。
- 不重构用户没有要求重构的代码。发现问题写入 TASKS.md 的 backlog，不擅自动手。
- 敏感信息（密钥、密码、用户数据）永不写入任何管理文件。

## File Definitions

初始化管理文件时，优先复制 `assets/templates/` 下的对应模板（CLAUDE.md、spec-template.md、TASKS.md、DECISIONS.md、HANDOFF.md）再填充内容，而不是从零生成——模板保证结构一致，跨项目可比。

### CLAUDE.md（项目宪法）

项目根目录。任何档位都必须有。控制在 100 行以内，包含：

```markdown
# <项目名>

## 目标
一句话说清这个项目为谁解决什么问题。

## 技术栈
语言、框架、关键依赖及版本。禁止引入的库单独列出。

## 约定
目录结构、命名规范、代码风格、错误处理方式。

## 红线
- 不做什么（永久性 Non-Goals）
- 不碰哪些文件/目录
- 哪些操作必须先问用户（删数据、改 schema、发请求到外部）

## 当前档位
G1 / G2 / G3，以及升档条件。
```

### specs/（意图层，G2+）

每个功能一个文件：`specs/NNN-<feature-name>.md`，编号递增。模板：

```markdown
# NNN: <功能名>

## 要什么
用户视角描述行为，不描述实现。

## 不做什么
本 spec 明确排除的范围。

## 验收清单
- [ ] 可执行的验证步骤，能跑命令就写命令
- [ ] 边界情况

## 实现约束
仅在必要时写：必须用/不能用的方案。

## 状态
draft / approved / done / superseded-by-NNN
```

写作纪律：可执行命令比描述性文字有效十倍；验收清单是给 AI 自查用的，不是给人看的装饰。

### TASKS.md（状态层，G2+）

项目根目录，单文件，三段式：

```markdown
# Tasks

## Now（本次会话正在做，最多 3 项）
- [ ] <任务> (spec: NNN)

## Next（已排序的待办）

## Done（倒序，保留最近 20 条，附 commit hash）

## Blocked
- <任务>：卡点描述，需要用户决策的写明问题
```

### DECISIONS.md（决策层，G2+）

轻量 ADR，追加式，永不删除，只标记废弃：

```markdown
- 2026-07-04: 选 SQLite 而非 Postgres。理由：单机部署、无并发写压力。备选：Postgres（部署成本高）。Confidence: high.
- 2026-06-20: [已废弃 → 见 07-04] ...
```

### 测试（验证层，G3）

- 每个 approved 的 spec 对应至少一个测试文件，测试名引用 spec 编号。
- AI 声称"完成"的唯一合法依据是测试通过的输出，不是 AI 的自我报告。
- 无测试框架的项目，先建最小测试脚手架，再写功能。

## Session Protocol（会话接班协议）

开工（每次会话开始）：
1. 读 `CLAUDE.md` → 读 `TASKS.md` 的 Now/Blocked → 读相关 spec。
2. 用一句话向用户确认本次会话目标，对齐后再动手。

干活：
3. G2+ 且是新功能 → 先写/更新 spec，请用户确认后再写代码。
4. 小步提交，每个任务完成即 commit。

收工（会话结束前，或上下文接近耗尽时主动执行）：
5. 更新 TASKS.md：Now 清空或移入 Blocked，Done 追加。
6. 有新决策写入 `DECISIONS.md`。
7. 给用户一段 30 字以内的「接班摘要」：下次会话从哪里继续。

## Handoff Protocol（跨界面交接协议）

适用场景：方案在一个界面里聊成型（对话、白板、文档），要交给另一个界面去实现（编码工具、另一个模型、另一个人）。这是**冷启动**，与 Session Protocol（同一项目内的会话接班）和 Setup Workflow（接管已有的乱项目）并列，是第三个入口。

交接失败的形式不是对方看不懂，而是**对方不知道什么叫做对了**。一份写得漂亮的需求文档，实现方只能猜验收标准；猜错了要读完整个实现才发现。所以交接物的本质不是文档，是**可执行的验收标准**。

### 交接包：一份清单 + 五件套

在项目根目录建 `HANDOFF.md` 作为总清单（模板见 `assets/templates/HANDOFF.md`），并附以下五个文件：

| 件 | 内容 | 形态要求 |
|---|---|---|
| 1 约束 | 数据结构、接口、字段定义、取值范围 | **机器可读**（JSON Schema、类型定义、DDL），不是散文描述 |
| 2 验收器 | 判定"做对没有"的脚本 | **一条命令能跑完**，退出码区分通过/致命/警告 |
| 3 正样本 | 一个完整、正确的实例 | 能通过验收器 |
| 4 反样本 | 故意注入错误的实例 | **必须能让验收器报错** |
| 5 缺口清单 | 已知缺什么、接口留在哪、为什么现在没做 | 写在 `HANDOFF.md` 里 |

前三件大家都会想到。**第 4 件和第 5 件是拉开差距的部分**：

- **反样本**：绝大多数规格只描述成功长什么样。只描述成功的规格是不可校验的——实现方无从知道边界在哪。反样本告诉它失败长什么样。
- **缺口清单**：主动申报"这里缺数据/缺依赖，接口留好了但没实现"。不写这段，实现方会悄悄造一个看起来能跑的假实现填坑，而这类错误要到很久以后才会暴露。

### 验收器的硬要求

- 一条命令跑完，不需要人工判断。
- 报错必须定位到具体字段和具体原因，不能只说"校验失败"。
- 区分致命与警告：致命回炉，警告进人工队列。
- **交出去之前，先用反样本自测一遍，确认它真的会报错。** 一个从不报错的验收器比没有验收器更危险——它给人虚假的安全感。

### 交接前的三问复核（人这一侧）

批准方案、打包交出去之前，必须由懂业务的人过一遍这三问。这是人在整个协作里价值最高的动作，比审规格细节重要得多——规格细节模型写得比人快也比人全。

1. **前提检验**：这个方案是不是从别的领域搬来的成熟模式？那个领域的前提在这儿成立吗？
   （模型最典型的设计失效方式，是迁移一个相邻领域的成熟模式却没重新检验前提。它的表现形式是"方案看起来很专业、很成体系"，因此特别难被发现。）
2. **规模检验**：规模翻五倍，这个架构是更贵还是更便宜？
   （判断架构的标准不是"现在够用"。好架构在规模变大时单位成本下降。）
3. **可见性检验**：哪些层在最终产品的界面上看不见？
   （看不见的层最容易被实现方悄悄跳过，因为跳过了产品看起来一样完整。为每个不可见层单独指定一条验收命令。）

### 交接后的回收

实现方交付后，交接发起方要做三件事，否则交接包会和实现脱节：

1. 跑一遍验收器，看反样本是否仍会报错（实现方可能为了让测试全绿而弱化验收器）。
2. 检查不可见层是否真的实现了，不看界面，看验收命令的输出。
3. 把实现过程中产生的新决策补写回 `DECISIONS.md`，把已填上的缺口从缺口清单划掉。

## Setup Workflow（初始化一个失控项目）

当用户带着一个已经混乱的 vibe coding 项目来时：

1. 扫描项目：目录结构、README、git log（如有）、依赖清单。
2. 判定档位，向用户确认。
3. 从代码反推生成 `CLAUDE.md` 初稿，未知项标 `待确认`，请用户补齐红线。
4. 从 git log 和代码现状反推 `TASKS.md`：已完成的进 Done，明显的半成品进 Blocked。
5. 能从代码中辨认出的重大选型，反推写入 `DECISIONS.md`，标注 `Basis: 代码反推，待用户确认`。
6. 不为存量功能补写 spec；从下一个新功能开始执行 spec 纪律。
7. 输出一份简短的接管报告：档位、已建文件、待确认项。

## Anti-Patterns（本技能明确反对）

- 为 G1 项目生成成套规范文档（用流程杀死原型速度）。
- 一个 spec 写 2000 行（规范冗长度与 AI 遵从度没有线性关系）。
- 用文档承诺代替测试验证。
- 把 TASKS.md 当聊天记录，把 DECISIONS.md 当日记。
- AI 自治式连续执行多个任务而不回到用户确认（正确模式是人机交替）。
- 交接时给出的是写得漂亮的需求文档，而不是能跑的验收器。
- 交接包只有正样本，没有反样本。
- 验收器从未用反样本自测过，全绿只证明它没在工作。
- 不申报已知缺口，于是实现方悄悄造了一个假实现。
- 把确定性可算的字段交给模型生成，再用多次生成投票去纠错。

## Final Response

每次会话结束时报告：完成的任务与 commit、更新的管理文件、新增决策、Blocked 项、接班摘要。保持简短。

交接场景下额外报告：交接包五件套是否齐备、反样本自测结果、三问复核中用户尚未确认的项。
