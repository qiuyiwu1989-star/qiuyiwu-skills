# 判断库架构

把信息系统从**存笔记**改造成**存判断**。

笔记系统存「说过什么」，靠相似度找回来。
判断系统存「谁认为什么、何时开始这么认为、后来变了没有、依据是什么」，能被追问、被推翻、被兑现。

**本 skill 是作业程序，不是读物。** 触发后按下面四步执行，产出交付物。

---

## 执行流程

### 第 0 步 · 判断该不该用

不适用的情况，**直接说明并停止**，不要硬套：

- 用途就是存证与检索原文（档案、合规留痕）→ 判断层是负担
- 系统里不存在「观点」，只有结构化事实（订单、日志、传感器读数）
- 用户要的是检索效果提升 → 那是召回与重排问题，本方法不解决

### 第 1 步 · 五问诊断

读 `references/diagnosis.md`，按其中的提问顺序和判据执行。

**这一步必须拿到用户系统的真实结构**（表结构、字段类型、或对数据模型的描述）。
拿不到就问，不要凭产品介绍猜。

五问全部合格 → 系统已是判断库，输出结论并停止。
**任意一条不合格 → 进入第 2 步。**

### 第 2 步 · 出诊断报告

用 `templates/diagnosis-report.md` 生成报告。

报告必须包含：每条不合格项 + 它已经或将要导致的**具体故障**（不是抽象风险）。
故障描述从 `references/failure-catalog.md` 取，**引用时保留案例编号**。

### 第 3 步 · 出迁移计划

读 `references/migration.md`，用 `templates/migration-plan.md` 生成计划。

计划必须按依赖排序，并明确标出：哪几步需要数据库迁移、哪几步需要回填、
哪一步是唯一的硬工程。**不要给出「全部重写」的建议**，本方法是增量改造。

### 第 4 步 · 交付验收判据

从 `references/acceptance.md` 取七条判据，逐条写成用户可自行执行的检查。

**不要口头保证效果。** 交付判据，让对方自证。

## 核心结论速查

细节在 references，这里只放执行时最常用的判断：

**判断的五位结构**（缺一不可）
```
谁认为(holder) · 关于谁(subject) · 什么陈述 · 何时成立(as_of) · 依据在哪(provenance)
+ 演变：被哪条取代 / 何时失效——不删除
```
最常漏第一位「谁认为」；第二常漏「何时成立」（用入库时间将就）。

**四条不变量**：身份唯一 · 溯源完整 · 演变可追 · 归属明确。
破一条，过去积累的全部判断贬值一次。

**分层判据**（拿这句判任何模块该放哪）
> 没人在的时候还会自己跑的，属大脑层；没人看就不产生价值的，属应用层。

**两道膜是唯一写入通道**：入库守卫（来源·主张者·作用域）、回写守卫（应用不得直写状态）。
接入 agent 之前，回写守卫必须先有。

**反馈信号接线**（唯一有同行评议证据的一条）
> 用它决定「推不推给用户」——可以。用它决定「判断可不可信」——不可以。

## 边界（必须主动告知用户）

- **不解决内容质量**：提炼判断的模型能力、提示词工程不在范围内
- **不解决检索算法**：向量召回、重排序请另找方法
- **不承诺量化收益**：「越用越聪明」截至本方法编写时**没有经得起对抗核查的公开量化证据**。
  本方法只保证信号回路接对位置，不保证接对之后提升多少
- **规模假设**：面向个人到中小团队量级语料。超大规模下实体解析的成本结构会改变

**时效**：判断结构、四不变量、两道膜与技术栈无关，长期有效。
反馈信号两条结论来自公开论文，原领域是代码补全，迁移到其他产品属合理推断而非已证。
