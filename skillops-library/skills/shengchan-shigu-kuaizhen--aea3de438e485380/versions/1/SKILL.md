# 生产事故快诊

原则：**证据先行，公网侧先行，统计先行。** 不带假设连服务器，不看单条错误下结论。

## 第 0 步：先想"今天我改了什么"

真实事故排行第一名的根因是**自己刚做的变更**（部署重启杀任务、改路由没同步改健康检查、
看门狗误判 307 每 2 分钟重启一次×439）。诊断前先列出 24h 内自己动过的东西。

## 第 1 步：公网侧取证（不碰服务器）

```bash
# 本机可能有代理劫持 curl —— 必须 --noproxy '*'，否则结论全错
curl -s --noproxy '*' -o /dev/null -w '%{http_code} t=%{time_total}s' --max-time 15 https://域名/健康路径
dig +short 域名 A                     # DNS 指到哪了？（通配符会盖掉单条记录，反复回退）
echo | openssl s_client -connect IP:443 -servername 域名 | openssl x509 -noout -subject -dates  # 证书对不对/过期没
curl -s --noproxy '*' --resolve 域名:443:IP ...   # 强制打到指定机器，绕开 DNS 排除法
```

判读：
- DNS 指错机 → 域名解析问题（通配符覆盖、缓存），机器本身可能没病。
- TLS 报过期/错名 → 打到了错的机器或旧证书，同上。
- HTTP 200 但巨慢 → 看 TLS 握手耗时；握手秒级=服务器 CPU 被打满（共享机邻居）。
- 000/超时 → 才是真的够不着。

## 第 2 步：区分"用户侧"与"管理侧"

**网页飞快但 SSH 卡死 = 用户没事，是登录 shell/磁盘 IO 被邻居打满。** 不要慌，更不要宣布宕机。
反过来 SSH 好好的但网页 502 = 进程/端口问题。两条路是独立的。

## 第 3 步：服务侧（能连上时，一条 ssh 拿全，别挤牙膏）

```
pm2 list · pm2 describe <app>   # 看 ↺ 重启数！ 439 次=重启循环，0 次久 uptime=进程被清
ss -ltnp | grep <port>          # 端口在不在听
tail 看门狗日志                  # 是不是"保护者"自己在杀（307→restart 循环）
pm2 logs --err --lines 25       # 崩溃循环中的 EACCES 等常是连带，先停循环再判断
uptime / free                   # load 正常就不是资源问题
```

## 第 4 步：数据侧——归类统计，不看单条

```sql
select status, count(*) from <任务表> group by status;
select left(error_message,40), count(*), max(created_at) from <任务表>
 where status='failed' group by 1 order by 2 desc;
```
- 错误只有两三类 → 各个击破；"timeout"要查是真超时还是**清扫器给僵尸打的标**。
- 卡在中间态的任务 = 进程重启时被杀的 inline 任务（谁重启的？回第 0 步）。

## 第 5 步：根因四分法 + 防复发

| 根因 | 特征 | 防复发 |
|---|---|---|
| 自己的变更 | 时间与部署/配置改动吻合 | 发布窗口冻结；改路由时 deploy+watchdog+监控**同改** |
| 共享机邻居 | load 高/IO 卡/进程被清但代码没动 | systemd 自启 + 看门狗 + 迁独立机（治本） |
| 代码 | 错误信息指向明确 stack | 修 + 测试盖住 |
| 外部 | DNS 回退/证书/上游 API | 记入 memory，给用户明确的"你要做的一件事" |

看门狗判活准则：**只有 000（连不上）或 5xx 才算挂**，2xx/3xx 都算活——否则路由一变它就成了凶手。

## 第 6 步：收尾三件事

1. 向用户报告用 **根因链**（A 导致 B 导致 C），不是现象罗列；自己埋的雷要直说。
2. 把根因 + 修法 + 教训**当场写入 memory**。
3. SSH 通道卡死时**别连环重试**——每次超时留下的僵连接会把 sshd 堵得更死。停手，
   给用户两条路：等自愈 / 控制台重启（重启的决定永远留给用户）。
